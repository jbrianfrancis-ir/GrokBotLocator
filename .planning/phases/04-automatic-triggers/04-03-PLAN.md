<objective>
The significant-change decision, separated from the wake that triggers it: given the last ping's
coordinate and a new fix, did the phone actually move 500 m? Pure, so it is provable without a device.
</objective>

<context>

.planning/REQUIREMENTS.md REQ-06 — "at least 500 m (fixed, not configurable)"; acceptance requires

  <name>Task 1: DisplacementGate</name>
  <files>src/Triggers/DisplacementGate.swift</files>
  <action>Two declarations, `import CoreLocation` + `import Foundation`:

`struct TriggerCoordinate: Sendable, Equatable` — `let latitude: Double`, `let longitude: Double`, plus `init(latitude:longitude:)`. A tiny value type rather than passing `CLLocationCoordinate2D` around: that type is not `Equatable` and carries no `Sendable` guarantee this codebase wants to lean on. Add `init(fix: LocationFix)` reading `fix.latitude`/`fix.longitude`.

`struct DisplacementGate: Sendable, Equatable`:
- `static let minimumMetres: Double = 500` — a `static let` with no initialiser parameter and no setter, so REQ-06's "fixed, not configurable" is enforced by the type rather than promised in a comment.
- `static func distanceMetres(from: TriggerCoordinate, to: TriggerCoordinate) -> Double` — `CLLocation(latitude:longitude:).distance(from:)`, which is the ellipsoidal distance CoreLocation itself uses.
- `static func shouldPing(from reference: TriggerCoordinate?, to candidate: TriggerCoordinate) -> Bool` — `true` when `reference == nil`; otherwise `distanceMetres(...) >= minimumMetres`.
Header comment states, in prose: the significant-change callback fires on cell-tower handoffs and is not a 500 m guarantee (RESEARCH Q3), which is the whole reason this type exists; and the no-reference behaviour is a BACKSTOP decision this phase's requirements do not settle (see this plan's `backstop_truths`).
No `Date()`, no `CLLocationManager`, no `FileManager`, no stored mutable state anywhere in the file.</action>
