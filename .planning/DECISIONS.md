## 2026-09-10 19:10 · checkpoint-decision
- **asked**: The architecture review found `ARCHITECTURE.md` contradicting itself, with both halves biting phase 03 (the durable queue). (1) Line 35 mandates an on-disk `Codable` queue as the durability mechanism while the Forbidden list bans "storing or logging ... raw coordinates" — a queue of `PingPayload` values IS raw coordinates on disk, and phase 02 already ruled in the strict direction (`PingHistory` is session-only, and says so in a comment), which made phase 03's entire deliverable illegal as written and phase 04 worse, since every automatic trigger queues a position while the app is asleep. (2) The wire format is pinned to exactly four keys with no timestamp (`LocationFix.timestamp` is dropped at the bridge), so a ping queued in a dead zone on Monday and drained Tuesday would arrive indistinguishable from a fresh fix — while SC-02 explicitly accepts that delivery lag, which means the receiver must be able to tell. Amend the law, keep it strict and re-scope phase 03, or plan 03 against the contradiction?
- **answered**: AMEND BOTH. Verbatim: "amend architecture for the queue and add a timestamp key". The queue file is now the ONE sanctioned store for coordinates, narrowly: `.completeFileProtectionUnlessOpen`, excluded from backups, each entry deleted on delivery, never copied elsewhere — a queue that keeps delivered pings would be a location history, which is not what it is for. Logs, analytics, `UserDefaults` and the in-memory history stay off limits, and the Forbidden entry now names the exception so the two clauses no longer contradict. The wire format gains a fifth key, `at`, the ISO-8601 time of the FIX (not the POST), in pinned order after `label`; the smoke gate's assertion and REQ-02's acceptance criterion were updated to match.
- **note**: the code change is NOT in this commit. `PingPayload` composes the wire bytes by hand (because `JSONEncoder`'s key order is non-deterministic), so adding `at` touches the encoder, its six tests, and the smoke assertion — that is phase 03's first task, and doing it there keeps the contract change and its tests in one reviewed diff. Until it lands, the shipped app still sends four keys, so phase 02's unrun REQ-02 acceptance check should be run against the FIVE-key format only after phase 03's first task, or re-run afterwards.
